# White-label builds

1. Clone this repo recursively: `git clone --recurse-submodules https://github.com/SpaceWorks-HQ/SpaceWorks-Android.git`. `design/` follows the Design-Kit `main` pin `b2aa5bb` (SpaceWorks-Labs/SpaceWorks-Design, 0.12.0); review token changes before updating its commit.
2. Edit only `branding/brand.json` and assets next to it. Set `app_name`, a unique `android_application_id` owned by your organisation, `app_icon` (SVG containing paths and optional rounded rectangles), and `theme_tokens` (same semantic light/dark token shape). Supply your actual support and privacy HTTPS URLs before store submission; null values intentionally indicate owner setup is outstanding.
3. Set `server_url` to your HTTPS deployment origin to lock the build to it. Leave null for first-launch server entry. The app performs generated `/api/v1/health/` validation before entering the shell. Official builds never bundle a staging URL or credentials.
4. Install Java 21, Python 3, Android SDK platform 36/build tools and run `./gradlew lint test assembleDebug`. Gradle reads the identity/name/server directly and regenerates the semantic Compose theme and vector launcher icon. `./gradlew :app:openApiGenerate` regenerates the API client.
5. Create your own Google Play Console application and enable Play App Signing. Store your upload keystore/passwords in CI secrets. Configure release signing in the private build environment; the repository does not include an owner upload key or release signing configuration. Review the signed release's package ID, certificate, version and icon before upload.
6. Create your own Firebase project and Android app matching the application ID. Enable/link Play Integrity to your own Play application, register the actual signing certificates and configure the backend app allowlist. Inject runtime Firebase configuration privately; token registration is gated and must not start from onboarding or demo. APNs applies to the companion iOS build and needs your own Apple account and key.
7. Complete privacy policy/Data safety details, reviewer demo account, closed testing and signing with your own accounts in A7/A8. Build a signed AAB (`bundleRelease`) after release signing is configured and publish through your Play Console.

No secrets, signing keys, `.p8` files, Firebase config or test credentials are committed. Interface text and display headings use Outfit (display 800, light display 300) and one accent phrase Unbounded, with native Material sizes and system font scaling. Debug APKs and unsigned CI release outputs are development/compile evidence. See [RELEASE-READINESS.md](RELEASE-READINESS.md) for the exact checks, owner inputs, privacy review and distribution evidence. The owner's batch workflow permits tested phases on `dev` before the final reviewed merge.

Auth/intro branding also reads `logo_symbol`, `logo_symbol_reversed`, `logo_symbol_one_colour_ink` and the equivalent `logo_stacked` paths from `brand.json`. Supply native-vector-compatible SVG masters with their original view boxes; keep the dedicated symbol/stacked clear space and do not animate/recolor/tint the logo. Mobile motion comes from this app repository's `tokens/mobile-motion.json` and UX guidance from `docs/mobile-auth-ux-spec.md`; system animation-off settings suppress custom movement/opacity transitions. The existing Design submodule supplies brand assets and semantic colors; mobile-specific files are maintained in the app repositories. The `font_sans` and `font_accent` paths select WOFF2 inputs (Design-Kit Outfit and Unbounded); display headings use the sans variable font at 800 (light display 300). `scripts/brand_fonts.py` decodes them to native TTF resources during `prepareBrand` with fontTools (`brew install fonttools`). A `null` accent falls back to the sans face; without fontTools the platform font is used. Bundle only open-licensed fonts and ship the licence of every font you bundle. See [font provenance](licenses/FONT-PROVENANCE.md).

Native Google acquisition uses Credential Manager 1.6.0 and the compiler-compatible GoogleID 1.1.1. The app passes `/config` `native.providers.google.android_client_id` as Credential Manager's `serverClientId`, so the server's "Google android client id" field must hold a **Web application** OAuth client ID; register an Android OAuth client for your package and signing SHA-1 in the same Google Cloud project. Production device sign-in also needs your Play Integrity Cloud project number (`play_integrity_cloud_project_number` in `brand.json`), and each OIDC provider must allow the redirect `{applicationId}:/oidc`. Release signing reads `SPACEWORKS_UPLOAD_KEYSTORE`, `SPACEWORKS_UPLOAD_KEYSTORE_PASSWORD`, `SPACEWORKS_UPLOAD_KEY_ALIAS` and `SPACEWORKS_UPLOAD_KEY_PASSWORD` from the private environment. See [NATIVE-CONTRACT.md](NATIVE-CONTRACT.md). The small Google G is Google's unchanged official sign-in asset ([source](https://developers.google.com/static/identity/images/g-logo.png), [branding requirements](https://developers.google.com/identity/branding-guidelines)); provider styling is intentionally independent of the app palette. No client secret is bundled. DEBUG preview providers never call Google/Apple/SSO/SMS SDKs or your backend; release omits their implementation and Explore demo entry.

Payment SDK styling uses their documented native appearance interfaces. Stripe receives both semantic brand palettes, 10 dp control corners, standard SDK text sizing, and a native Outfit XML family with explicit 400/500/600/700 weights. Stripe retains its native layout, accessible controls and system light/dark selection. Razorpay Android Standard Checkout receives only the documented `theme.color` accent; merchant identity/logo remain deployment/provider supplied. Its current Android API does not document a custom font or complete dark palette. The app does not inject unsupported options or restyle provider verification screens. These appearance settings do not confirm payment: existing server refetch and callback ownership checks remain authoritative.

Supported provider appearance references: [Stripe Android Appearance API](https://docs.stripe.com/elements/appearance-api/mobile?platform=android), [Razorpay Android Standard integration options](https://razorpay.com/docs/payments/payment-gateway/android-integration/standard/integration-steps/).

Native motion uses the existing mobile motion tokens and observes Android's animation-duration setting through the shared production theme. The supplied logo stays static. Onboarding panel transitions and guide disclosures suppress custom motion when system animation is off. Outcome feedback uses the one-argument `View.performHapticFeedback` API only for explicit progression, guarded auth outcomes and fresh server-recorded member/staff actions. Lifecycle, current owner and duplicate-completion gates suppress stale or background effects; Android retains control of touch-feedback settings and hardware support. No vibration permission or setting-bypass flags are required.

Telemetry is optional. The `telemetry` block in `brand.json` (`sentry_dsn`, `sentry_environment`, `sentry_traces_sample_rate`, `posthog_api_key`, `posthog_host`, `clarity_project_id`) holds public values only; each can be overridden with Gradle properties (`-Pspaceworks.sentryDsn=` …) or `SPACEWORKS_*` environment variables in CI. Firebase Analytics uses the same private `app/google-services.json` as FCM (never committed). A provider with no value is off and its consent switch hidden; with none configured, no consent prompt or Privacy entry appears. Set your Clarity project's masking mode to Strict. Debug builds never send unless `-Pspaceworks.telemetryDebug=true`. See [TELEMETRY.md](TELEMETRY.md) and complete your store privacy answers from [STORE-LISTING.md](STORE-LISTING.md).

The Patch mascot appears on main empty lists and the first intro page; it comes from `design/mascot` (`dark/` variants on the dark theme) and is static when system animations are off. Membership card and event ticket use the kit's `cards.aurora` colours.
